1. PROJECT OVERVIEW & CORE GOALS
================================================================================

This project is a distributed, high-performance, and secure Competitive
Programming (CP) Online Judge Engine (similar to systems powering LeetCode,
Codeforces, HackerRank, and SPOJ).

Its core responsibilities are:
1. Accept untrusted code submissions in languages like C++ from users.
2. Queue submissions asynchronously without blocking the user-facing web server.
3. Execute code inside isolated, secure, and resource-constrained Docker sandboxes.
4. Enforce strict CPU time limits, RAM memory limits, process limits, and network isolation.
5. Accurately verify outputs against hidden and public test cases.
6. Return immediate live verdicts (AC, WA, TLE, MLE, CE, RE) to clients via WebSockets
   and REST APIs.

3. CORE COMPONENTS & DEEP DIVE
================================================================================

--------------------------------------------------------------------------------
3.1. REST API Server (src/api/index.ts & src/api/routes.ts)
--------------------------------------------------------------------------------
Built with Express.js and TypeScript. It exposes the following endpoints:

- POST /api/submissions
  Payload: { problemId: 1, userId: 1, language: 'cpp', sourceCode: '...' }
  What it does:
  a. Validates inputs.
  b. Persists the submission to PostgreSQL with initial status "QUEUED".
  c. Pushes a job to the BullMQ Redis queue ('submissions').
  d. Returns HTTP 201 with the created submission record immediately (non-blocking).

- GET /api/submissions/:id
  Returns the current status, verdict, execution time, and error logs for a submission.

- POST /api/problems
  Creates a coding problem with statement, time limits (e.g. 1000ms), and memory limits.

- POST /api/problems/:id/testcases
  Adds input and expected output test cases (either public or hidden).

--------------------------------------------------------------------------------
3.2. Real-Time WebSockets Server (src/api/ws.ts)
--------------------------------------------------------------------------------
Why WebSockets?
In a competitive programming platform, users shouldn't have to repeatedly refresh
the page to see their verdict. As soon as a background worker changes status from
QUEUED -> RUNNING -> COMPLETED (AC / WA / TLE), the worker publishes the event to
Redis, and the WebSocket server broadcasts it directly to connected browser clients.

How it works:
1. An HTTP server is created and wrapped with the 'ws' library.
2. A dedicated IORedis subscriber listens to the 'submission-updates' channel.
3. Whenever a message arrives on Redis:
   redisSub.on('message', (channel, message) => {
       // Broadcast JSON to all active WebSocket connections
   });

--------------------------------------------------------------------------------
3.3. Job Queue System (BullMQ + Redis) (src/shared/queue.ts)
--------------------------------------------------------------------------------
Why use BullMQ?
Judging code is CPU and I/O intensive. If 1,000 users submit code at the exact same
second, executing all 1,000 immediately would freeze the API server and crash the host machine.

BullMQ acts as a buffer:
- The API server accepts requests instantly and queues them into Redis.
- Workers pull jobs at a controlled, sustainable rate.
- Supports automatic exponential backoff retries if a transient system error occurs.

--------------------------------------------------------------------------------
3.4. Database Layer (PostgreSQL + Prisma ORM) (prisma/schema.prisma)
--------------------------------------------------------------------------------
Prisma provides type-safe access to PostgreSQL. Key data models:

- User:
  Represents programmers and authors.
- Problem:
  Stores title, statement, timeLimitMs (default: 1000ms), memoryLimitKb (256MB).
- TestCase:
  Belongs to a Problem. Holds 'input' string, 'expectedOutput' string, and 'isHidden'.
- Submission:
  Tracks the submission lifecycle:
  * status: QUEUED | RUNNING | COMPLETED | SYSTEM_ERROR
  * verdict: AC | WA | TLE | MLE | RE | CE
  * timeMs: Execution time in milliseconds
  * memoryKb: Memory used
  * errorOutput: Compilation or runtime crash traces

--------------------------------------------------------------------------------
3.5. Standby Sandbox Pool Manager (src/worker/sandbox/pool.ts)
--------------------------------------------------------------------------------
The Problem:
Booting up a Docker container takes ~1 to 2 seconds of "cold start" latency.
Waiting 2 seconds for a container to boot before running a 50ms C++ program makes
the judge feel very slow.

The Solution (Warm Standby Pool):
1. The StandbyPoolManager pre-warms a configurable number of idle sandbox containers
   (default: 2 containers) using:
   docker run -d --label cp-judge-sandbox=true --network none --memory=256m \
          --pids-limit=64 --cap-drop=ALL gcc:latest sleep infinity
2. When a submission arrives, worker.getContainer() grabs an already-running container
   instantly (0ms latency).
3. The submission is evaluated inside this warm container.
4. Once evaluated, the container is destroyed (docker rm -f) to prevent any leftover
   files or security contamination.
5. In the background, the pool asynchronously launches a fresh container to replace it.
6. Automatic Lifecycle Management:
   - On Startup: Automatically finds and purges any stale containers labeled
     'cp-judge-sandbox=true'.
   - On Shutdown (Ctrl+C): Catches SIGINT/SIGTERM and cleanly stops all standby containers.

--------------------------------------------------------------------------------
3.6. Language Judge: C++ (src/worker/judges/cpp.ts)
--------------------------------------------------------------------------------
Coordinates compilation and test evaluation inside the assigned container:
1. Writes the user's C++ code to a temporary file on the host (e.g. main.cpp).
2. Copies it into the container using 'docker cp'.
3. Compiles via 'docker exec <containerId> g++ -O2 -w -std=c++17 /tmp/main.cpp -o /tmp/a.out'.
   - If exit code != 0: returns Compile Error (CE) with compiler error text.
4. For each test case:
   - Copies input data to /tmp/input.txt inside the container.
   - Runs: docker exec <containerId> bash -c "timeout <limit>s /tmp/a.out < /tmp/input.txt"
   - Captures output and measures execution duration using high-resolution timers.
   - Compares stripped, normalized output against expected output.

4. SECURITY & CONTAINER HARDENING (HOW UNTRUSTED CODE IS TAMED)
================================================================================

Running arbitrary user-submitted code is dangerous. A user might submit malicious
code trying to delete files, launch network attacks, or crash the machine.
The engine applies 5 layers of container defense:

1. Network Disablement (--network none):
   The container has NO internet access and NO local network access.
   - Prevents downloading malicious payloads or botnet scripts.
   - Prevents scanning your internal network or stealing database credentials.

2. CGroup Memory Limits (--memory=256m):
   The Linux kernel cgroup hard-caps memory to 256MB.
   If user code attempts to allocate 1GB of memory (e.g. while(1) new int[1000000];),
   the Linux kernel OOM (Out Of Memory) killer terminates the process with exit code 137.
   The judge detects 137 and marks the verdict as "MLE".

3. Process Limit / Fork Bomb Protection (--pids-limit=64):
   A classic attack is a Fork Bomb (e.g. while(1) fork();) which spawns processes
   exponentially to crash the host CPU.
   With --pids-limit=64, the container cannot create more than 64 processes. Any further
   fork() call fails with EAGAIN.

4. Dropped Capabilities (--cap-drop=ALL):
   Drops all Linux root capabilities (like CAP_SYS_ADMIN, CAP_NET_ADMIN). Even if the
   code runs as root inside the container, it cannot alter system clocks, mount devices,
   or escape container namespaces.

5. CPU Execution Time Limits (Linux timeout utility):
   If code enters an infinite loop (while(true) {}), the Linux 'timeout' command sends
   SIGKILL after the allotted time window, yielding exit code 124 (verdict: "TLE").

5. END-TO-END SUBMISSION LIFECYCLE (STEP-BY-STEP TRACE)
================================================================================

Here is the exact journey of a submission through the system:

1. User submits code via HTTP POST:
   POST /api/submissions
   Body: { problemId: 1, userId: 1, language: 'cpp', sourceCode: '...' }

2. API Server:
   - Saves record into PostgreSQL with status = 'QUEUED'.
   - Enqueues job: queue.add('judge-submission', { submissionId: 42 }).
   - Sends response: HTTP 201 { id: 42, status: 'QUEUED' }.

3. Background Worker:
   - Worker picks up job 42 from Redis.
   - Updates DB status to 'RUNNING'.
   - Broadcasts 'RUNNING' status on Redis channel 'submission-updates' (WS pushes to UI).
   - Fetches problem test cases from DB.
   - Grabs a warm container from the StandbyPoolManager.

4. C++ Judge:
   - Compiles code inside container.
   - Runs container against each test case.
   - Evaluates outputs, execution times, and exit codes.
   - Destroys container and prompts pool to replenish a new standby container.

5. Finalization:
   - Updates DB record: status = 'COMPLETED', verdict = 'AC', timeMs = 174.
   - Broadcasts 'COMPLETED' with verdict 'AC' to WebSocket clients.
   - BullMQ job completes successfully.

6. CONCRETE TEST CASE EXAMPLES & VERDICT EXPLANATIONS
================================================================================

Problem 1: "A + B Problem"
Input: Two integers separated by space (e.g. "3 5")
Expected Output: Sum of integers (e.g. "8")
Time Limit: 1000ms | Memory Limit: 256MB

--------------------------------------------------------------------------------
Case 1: Accepted (AC)
--------------------------------------------------------------------------------
Source Code:
    #include <iostream>
    using namespace std;
    int main() {
        int a, b;
        if (cin >> a >> b) cout << a + b << endl;
        return 0;
    }
What happens:
- Compiles with exit code 0.
- Runs in 174ms (< 1000ms limit).
- Output matches expected output ("8" == "8").
Verdict: AC (Accepted)

--------------------------------------------------------------------------------
Case 2: Wrong Answer (WA)
--------------------------------------------------------------------------------
Source Code:
    #include <iostream>
    using namespace std;
    int main() {
        int a, b;
        if (cin >> a >> b) cout << a + b + 1 << endl; // Faulty logic!
        return 0;
    }
What happens:
- Output produced: "9"
- Expected output: "8"
- Judge detects discrepancy and flags failure immediately.
Verdict: WA (Wrong Answer)

--------------------------------------------------------------------------------
Case 3: Time Limit Exceeded (TLE)
--------------------------------------------------------------------------------
Source Code:
    #include <iostream>
    using namespace std;
    int main() {
        while(true) {} // Infinite loop!
        return 0;
    }
What happens:
- Program runs continuously without returning.
- After 2 seconds, the container timeout utility kills the process (exit code 124).
Verdict: TLE (Time Limit Exceeded)

--------------------------------------------------------------------------------
Case 4: Compile Error (CE)
--------------------------------------------------------------------------------
Source Code:
    #include <iostream>
    using namespace std;
    int main() {
        int a, b;
        cin >> a >> b;
        cout << a + b // Missing semicolon!
        return 0;
    }
What happens:
- g++ compiler fails with exit code 1:
  "error: expected ';' before 'return'"
- Judge intercepts compiler stderr output and attaches it to the submission record.
Verdict: CE (Compile Error)

--------------------------------------------------------------------------------
Case 5: Memory Limit Exceeded (MLE)
--------------------------------------------------------------------------------
Source Code:
    #include <iostream>
    #include <vector>
    using namespace std;
    int main() {
        vector<int*> ptrs;
        while(true) {
            ptrs.push_back(new int[1000000]); // Allocates hundreds of MBs
        }
        return 0;
    }
What happens:
- Process memory balloons past 256MB.
- Linux kernel cgroup OOM killer terminates the process immediately (exit code 137).
Verdict: MLE (Memory Limit Exceeded)

--------------------------------------------------------------------------------
Case 6: Security Resilience (Fork Bomb)
--------------------------------------------------------------------------------
Source Code:
    #include <unistd.h>
    int main() {
        while(1) {
            fork(); // Tries to spawn infinite processes
        }
        return 0;
    }
What happens:
- Code attempts process explosion.
- Once 64 processes are created, --pids-limit=64 prevents any more forks.
- Host machine CPU and memory remain completely unaffected.
- The timeout utility terminates the trapped container.
Verdict: TLE / RE (Successfully contained and neutralized)

7. HOW TO RUN, TEST, AND OPERATE THE ENGINE
================================================================================

Prerequisites:
1. Docker Desktop installed and running.
2. Node.js (v18+).

Step 1: Start Infrastructure (PostgreSQL & Redis)
    docker compose up -d

Step 2: Sync Database Schema (First Time)
    npx prisma db push

Step 3: Start the API Server (Terminal 1)
    npm run api
    -> Runs on http://localhost:3000

Step 4: Start the Judge Worker (Terminal 2)
    npm run worker
    -> Connects to Redis and pre-warms sandbox containers

Step 5: Run the End-to-End Test Suite (Terminal 3)
    npm run test
    -> Automatically seeds test problem and runs all 6 test cases

8. KEY ENGINEERING HIGHLIGHTS & RESUME / INTERVIEW TALKING POINTS
================================================================================

If discussing this project in technical interviews or on your resume:

1. Asynchronous Event-Driven Architecture:
   - Decoupled high-throughput web traffic from heavy compute jobs using Redis & BullMQ.
   - Real-time updates delivered over WebSockets using Redis Pub/Sub.

2. Zero Cold-Start Sandboxing (Standby Pool Manager):
   - Designed a warm container standby pool in Docker that eliminated 1-2 second container
     startup delays, reducing execution latency to sub-200ms.
   - Built automatic orphan cleanup with Docker labels and graceful process shutdown hooks.

3. Defense-in-Depth Container Hardening:
   - Enforced strict multi-layered isolation: --network none, memory cgroups (256MB),
     process limits (--pids-limit=64), and capability dropping (--cap-drop=ALL).

4. Production-Grade Robustness:
   - Database integrity with PostgreSQL & Prisma foreign keys.
   - Cross-platform support (Docker daemon abstraction works on Windows, Linux, and macOS).
